# Специфікація: промо-сайт книги (шаблон для нових проєктів)

Цей документ — технічне завдання для створення сайту-візитівки книги з формою замовлення.
Еталонна реалізація: проєкт **«Люди без облич»** (`TheFacelessPeople`).

**Правило №1 для агента:** функціонал має бути **ідентичним** еталону (див. розділ 4 «Функціональна специфікація»).
**Правило №2:** візуальний дизайн має бути **новим** — інша палітра, типографіка, настрій, підібрані під конкретну книгу. Структура секцій при цьому лишається тією ж.

## 0. Порядок роботи агента

1. Прочитати цей документ повністю.
2. Прочитати заповнений **Бриф** (розділ 1). Якщо якісь поля порожні або позначені `{{...}}` — **поставити користувачу питання і дочекатися відповіді**. Не вигадувати за користувача: ціни, посилання на оплату, тексти й контакти вигадувати заборонено.
3. Уточнити те, що впливає на роботу, але у брифі не покрито (див. розділ 1.9 «Питання, які варто поставити»).
4. Створити проєкт (розділ 2), реалізувати функціонал (розділ 4), дизайн (розділ 6).
5. Прогнати чекліст приймання (розділ 8).
6. Віддати користувачу список змінних оточення, які він має заповнити (розділ 5), і інструкцію деплою (розділ 9).

> **Важливо про Next.js.** У проєкті використовується Next.js 16+. Це **не той Next.js, який ви знаєте з тренувальних даних** — API, конвенції та структура файлів можуть відрізнятися. Перед написанням коду читайте актуальний гайд у `node_modules/next/dist/docs/`. Зважайте на попередження про застарілі API.

### 1.9 Питання, які варто поставити, якщо бриф неповний

- Точні ціни й повні підписи варіантів замовлення (вони показуються покупцю дослівно).
- Робоче посилання на оплату — його треба перевірити відкриттям.
- Чи стартуємо в режимі передзамовлення.
- Домен (потрібен для `metadataBase`, canonical і OG-тегів).
- Хто отримує сповіщення про замовлення і якими каналами.
- Чи є вимоги до кольорів/шрифтів, чи дизайн на розсуд агента.
- Чи потрібна сторінка з політикою конфіденційності / офертою (в еталоні її немає; для деяких платіжних провайдерів вона обов'язкова).

### 3.1 `config/book.ts` — обов'язкова вимога до нових проєктів

В еталоні ціни й підписи варіантів продубльовані у трьох місцях (константа `PRICES`, підписи в `<option>`, `variantLabel` в API) — при зміні ціни легко розсинхронити. **У новому проєкті винести це в один файл**, який імпортують і клієнт, і серверні роути:

```ts
// config/book.ts
export const BOOK = {
  title: "{{BOOK_TITLE}}",
  author: "{{AUTHOR_NAME}}",
  tagline: "{{GENRE_TAGLINE}}",
  shortDescription: "{{SHORT_DESCRIPTION}}",
  siteUrl: "{{SITE_URL}}",
  coverSrc: "/cover.jpg",
  paymentUrl: "{{PAYMENT_URL}}",
} as const;

export const VARIANTS = [
  { id: "{{VARIANT_1_ID}}", label: "{{VARIANT_1_LABEL}}", price: {{VARIANT_1_PRICE}} },
  { id: "{{VARIANT_2_ID}}", label: "{{VARIANT_2_LABEL}}", price: {{VARIANT_2_PRICE}} },
] as const;

export type VariantId = (typeof VARIANTS)[number]["id"];

export const PAYMENT_METHODS = [
  { id: "online", label: "Оплата онлайн" },
  { id: "cod", label: "Післяплата" },
] as const;

export const LINKS = [
  // рендерити тільки заповнені
  { label: "Telegram канал", href: "{{TELEGRAM_URL}}" },
  { label: "YouTube", href: "{{YOUTUBE_URL}}" },
  { label: "Підтримати автора", href: "{{DONATE_URL}}" },
];

export const REVIEWS = [
  { quote: "{{...}}", author: "{{...}}" },
];
```

Підпис у `<option>` формується як `${label} — ${price} грн`, серверна валідація перевіряє, що `variant` є серед `VARIANTS[].id`, у сповіщення йде `label`. Жодних магічних рядків у компонентах.

Це основна частина. Реалізувати треба **все** перелічене.

### 4.1 `app/layout.tsx`

- `lang="uk"` (або `{{SITE_LANG}}`), `suppressHydrationWarning`, `className` з CSS-змінними шрифтів + `h-full antialiased`.
- Два шрифти через `next/font/google`: основний (`--font-sans`) і акцидентний для заголовків (`--font-display`). **Обов'язково** `subsets: ["latin", "cyrillic"]` — інакше кирилиця поїде на фолбек.
- `metadata`:
  - `metadataBase: new URL(BOOK.siteUrl)`;
  - `title`, `description` (з брифу);
  - `alternates.canonical: "/"`;
  - `openGraph`: `type: "website"`, `url`, `siteName`, `title`, `description`, `images: [{ url: coverSrc, width: 1200, height: 630, alt }]`;
  - `twitter`: `card: "summary_large_image"`, `title`, `description`, `images`.
  - Рекомендація: для OG краще окреме зображення 1200×630 (`public/og.jpg`), бо вертикальна обкладинка в шерінг-картці обрізається. Якщо його немає — попередити користувача.
- `<Analytics />` з `@vercel/analytics/next` наприкінці `<body>`.
- `<body>` задає базові кольори теми і `min-h-full flex flex-col`.

### 4.2 `app/page.tsx` — секції (порядок обов'язковий)

1. **Header** — sticky, `z-40`, напівпрозорий фон із `backdrop-blur`, нижня межа. Ліворуч — маркер (крапка акцентного кольору) + назва книги капслоком із розрядкою. Праворуч — навігація-якорі, приховані на мобільному (`hidden md:flex`): «Про книгу», «Замовити», «Відгуки», «Посилання».
2. **Hero** — двоколонковий на десктопі (`lg:grid-cols-[1.1fr_0.9fr]`), одноколонковий на мобільному. Ліворуч: надрядок-жанр, `<h1>` з назвою, короткий опис, кнопка-CTA «Замовити книгу» → `#order`. Праворуч: обкладинка через `next/image` з `priority`, у декоративній рамці/підсвітці.
3. **`#about`** — заголовок секції + 4–7 абзаців тексту «Про книгу», ширина колонки ≈ `max-w-4xl`, комфортний `leading-relaxed`.
4. **`#order`** — контейнер `max-w-3xl`, усередині `<OrderForm />`.
5. **`#reviews`** — заголовок + сітка карток відгуків (`md:grid-cols-3`), кожна картка: цитата + ім'я автора внизу (`mt-auto`, щоб імена вирівнялися). Під сіткою — кнопка «Читати більше відгуків» на зовнішній ресурс (`target="_blank" rel="noreferrer"`), якщо посилання задане.
6. **`#links`** — двоколонковий блок: ліворуч заголовок і текст-підводка, праворуч — стовпчик кнопок-посилань + кнопка `<QuestionModal />` останньою.
7. **Footer** — `© {поточний рік} {назва книги}`, дрібним, по центру.

Сторінка є server component; жодних `"use client"` у `page.tsx`.

### 4.3 `components/OrderForm.tsx` (client)

**Поля форми** (усі, крім автографа, обов'язкові):

| Поле | Тип | Валідація |
| --- | --- | --- |
| Варіант замовлення | `select` з `VARIANTS` | required |
| Контакт для зв'язку | `text`, placeholder «Telegram / Facebook / Телефон» | required |
| Для кого автограф | `text`, placeholder-приклад | **необов'язкове** |
| ПІБ отримувача | `text` | required |
| Номер телефону | `tel` | required, `pattern="^(\+?380\|0)\d{9}$"`, `title` з поясненням формату |
| Місто / Село | `text` | required |
| Відділення `{{DELIVERY_SERVICE}}` | `text` | required |
| Спосіб оплати | `select`: онлайн / післяплата | required |

**Поведінка:**

- У шапці картки — блок «Вартість», що **реактивно** показує ціну обраного варіанта (`useMemo` від `form.variant`).
- Якщо `process.env.NEXT_PUBLIC_PREORDER_ENABLED === "true"` — над формою показується банер про передзамовлення. Порівняння регістронезалежне (`?.toLowerCase()`).
- Підпис кнопки залежить від стану: `«Надсилаємо...»` під час сабміту → `«Замовити і оплатити»` для онлайн-оплати → `«Замовити книгу»` для післяплати. Кнопка `disabled` під час відправки.
- POST на `/api/order` з тілом форми. Помилка → повідомлення «Не вдалося надіслати замовлення. Будь ласка, спробуйте ще раз.» під формою.
- Успіх → форма очищається, показується **модалка успіху**: «Дякуємо за замовлення!», текст про очікування відправки, номер замовлення з відповіді API, кнопка «Закрити». Для онлайн-оплати додається рядок-нагадування «Не забудьте виконати оплату замовлення».

**Онлайн-оплата — критична логіка (не спрощувати!).**

Браузери блокують `window.open`, викликаний після `await`, бо втрачається зв'язок із жестом користувача. Тому:

```tsx
const submit = async (event: React.FormEvent<HTMLFormElement>) => {
  event.preventDefault();
  setIsSubmitting(true);
  setStatus("idle");
  setNeedsManualPayment(false);

  let paymentWindow: Window | null = null;
  const isIOS =
    /iPad|iPhone|iPod/.test(navigator.userAgent) && !("MSStream" in window);

  // 1. Вкладку відкриваємо СИНХРОННО, до будь-якого await.
  if (form.paymentMethod === "online" && !isIOS) {
    paymentWindow = window.open("about:blank", "_blank");
    if (paymentWindow) paymentWindow.opener = null;
  }

  try {
    const response = await fetch("/api/order", { /* ... */ });
    if (!response.ok) throw new Error("Order failed");
    const { orderId } = await response.json();

    setStatus("success");
    setOrderMeta({ orderId, paymentMethod: form.paymentMethod });

    if (form.paymentMethod === "online") {
      if (isIOS) {
        // 2. iOS Safari блокує відкладені попапи — переходимо в тій самій вкладці.
        window.location.href = BOOK.paymentUrl;
      } else if (paymentWindow && !paymentWindow.closed) {
        try {
          paymentWindow.location.href = BOOK.paymentUrl;
          // 3. Перевіряємо, чи навігація відбулася; якщо ні — даємо ручну кнопку.
          window.setTimeout(() => {
            try {
              const href = paymentWindow.location.href;
              if (href === "about:blank" || href === "about:blank#") {
                setNeedsManualPayment(true);
              }
            } catch {
              // cross-origin читання впало → навігація успішна
            }
          }, 1000);
        } catch {
          setNeedsManualPayment(true);
        }
      } else {
        setNeedsManualPayment(true); // попап заблоковано
      }
    }

    resetForm();
  } catch (error) {
    console.error(error);
    setStatus("error");
    if (paymentWindow && !paymentWindow.closed) paymentWindow.close();
  } finally {
    setIsSubmitting(false);
  }
};
```

Якщо `needsManualPayment === true` — у модалці успіху показується кнопка **«Відкрити оплату»** (`<a target="_blank" rel="noreferrer">` на `paymentUrl`). Це страховка від блокувальників попапів: користувач ніколи не лишається без способу оплатити.

### 4.4 `components/QuestionModal.tsx` (client)

- Кнопка-тригер «Задати питання щодо замовлення» у секції `#links`.
- Модалка: фон-оверлей `fixed inset-0 z-50 bg-black/80`, картка з заголовком і кнопкою «Закрити».
- Поля: Ім'я (required), «Як з вами зв'язатися» (required), «Суть питання» — `textarea` (required).
- **Honeypot:** приховане поле `website` (`tabIndex={-1}`, `autoComplete="off"`, `className="hidden"`). Якщо воно заповнене — сервер тихо повертає `ok: true`, нічого не надсилаючи.
- **Кулдаун 60 секунд** після успішної відправки: кнопка `disabled`, підпис «Можна відправити через N с», лічильник через `setInterval` в `useEffect` з очищенням таймера.
- Статуси: успіх — «Дякуємо! Ми отримали ваше питання і відповімо якнайшвидше.»; помилка — «Не вдалося надіслати питання. Спробуйте ще раз.».

### 4.5 `app/api/order/route.ts`

- `export const runtime = "nodejs"` (потрібно для `googleapis` і `crypto`).
- `POST`: парсить JSON, перевіряє наявність усіх обов'язкових полів (`autographFor` — не обов'язкове) → `400 { error: "Missing field: X" }`.
- Валідує, що `variant` є серед відомих id, а `paymentMethod` ∈ {`online`, `cod`} → інакше `400`.
- Генерує `orderId`: `crypto.randomBytes(4).toString("hex").toUpperCase()` (8 hex-символів).
- Часова мітка: `new Date().toLocaleString("uk-UA", { timeZone: "Europe/Kiev" })`.
- Три канали доставки запускаються **паралельно** й **незалежно**:
  ```ts
  const [sheetOk, telegramOk, emailOk] = await Promise.all([
    appendToGoogleSheet(orderId, normalized).catch(() => false),
    sendTelegram(orderId, normalized).catch(() => false),
    sendEmail(orderId, normalized).catch(() => false),
  ]);
  ```
- Відповідь: `{ ok: true, orderId, notifications: { googleSheets, telegram, email } }`.
- Будь-яка неочікувана помилка → `500 { error: "Server error" }` + `console.error`.

**Канал Google Sheets.** Якщо немає `GOOGLE_SHEETS_SHEET_ID` / `CLIENT_EMAIL` / `PRIVATE_KEY` — повертає `false`, нічого не робить. Приватний ключ обов'язково через `.replace(/\\n/g, "\n")`. Авторизація — `new google.auth.JWT` зі скоупом `https://www.googleapis.com/auth/spreadsheets`. Append у `${sheetName}!A1`, `valueInputOption: "RAW"`, `insertDataOption: "INSERT_ROWS"`. Порядок колонок:

`Час | № замовлення | Варіант | Спосіб оплати | ПІБ | Телефон | Контакт | Місто | Відділення | Автограф`

(порожній автограф пишеться як `-`).

**Канал Telegram.** `POST https://api.telegram.org/bot{TOKEN}/sendMessage`, тіло `{ chat_id, text }`. Текст — той самий набір полів, по рядку на поле, з заголовком `Нове замовлення #{orderId}`. Порожній автограф → «не вказано».

**Канал Email (Resend).** `POST https://api.resend.com/emails` з `Authorization: Bearer {RESEND_API_KEY}`, тіло `{ from, to, subject, html }`. Тема: `Нове замовлення книги #{orderId}`. Тіло — `<h2>` + `<ul>` з тими ж полями.

> **Обов'язкове покращення для нового проєкту:** в еталоні дані користувача вставляються в HTML-лист без екранування. Це не XSS для покупця, але може зламати верстку листа. У новому проєкті прогнати всі значення через просту функцію екранування (`&`, `<`, `>`, `"`), перш ніж вставляти в HTML. Для Telegram — не використовувати `parse_mode` (тоді екранування не потрібне) або екранувати за правилами MarkdownV2.

### 4.6 `app/api/question/route.ts`

Те саме, простіше: `runtime = "nodejs"`, обов'язкові `name`, `contact`, `question`; перевірка honeypot `website` → ранній `{ ok: true }`; паралельні Telegram + Email; відповідь `{ ok: true, notifications: {...} }`; помилка → `500`.

### 4.7 Принцип «м'якої деградації»

Сайт має **приймати замовлення навіть коли жодна інтеграція не налаштована**. Відсутні env-змінні — це не помилка, а вимкнений канал. Покупець завжди бачить успішну модалку з номером замовлення. Це навмисно: краще отримати замовлення в лог Vercel, ніж показати покупцю помилку.

При цьому агент має **попередити користувача**, які канали лишилися невимкненими на момент здачі.

## 5. Змінні оточення

Створити `.env.example` у корені (сам `.env*` у `.gitignore`, у git не комітиться):

```bash
# --- Публічні (доступні в браузері) ---
NEXT_PUBLIC_PREORDER_ENABLED=false      # "true" вмикає банер передзамовлення

# --- Google Sheets (опційно) ---
GOOGLE_SHEETS_SHEET_ID=
GOOGLE_SHEETS_SHEET_NAME=Orders
GOOGLE_SHEETS_CLIENT_EMAIL=
GOOGLE_SHEETS_PRIVATE_KEY=              # з \n замість реальних переносів рядка

# --- Telegram (опційно) ---
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=

# --- Email через Resend (опційно) ---
RESEND_API_KEY=
RESEND_FROM_EMAIL=                      # адреса на верифікованому домені
RESEND_TO_EMAIL=
```

**Налаштування інтеграцій (інструкція для власника сайту):**

- **Google Sheets:** створити сервісний акаунт у Google Cloud → увімкнути Google Sheets API → створити JSON-ключ → взяти з нього `client_email` і `private_key` → **надати цьому email доступ «Редактор» до таблиці** (без цього кроку запис не працюватиме) → `SHEET_ID` — з URL таблиці. Перший рядок таблиці зробити шапкою з назвами колонок у порядку з розділу 4.5.
- **Telegram:** створити бота через `@BotFather` → отримати токен → написати боту будь-що → дізнатися `chat_id` через `https://api.telegram.org/bot<TOKEN>/getUpdates`. Для групи — додати бота в групу та взяти від'ємний `chat_id`.
- **Resend:** зареєструватися, верифікувати домен-відправник, створити API-ключ. `RESEND_FROM_EMAIL` має бути на верифікованому домені, інакше листи не підуть.
- **Оплата:** посилання на банку monobank (`https://send.monobank.ua/...`) або інший платіжний лінк. Це просто зовнішнє посилання — жодних платіжних даних сайт не обробляє й не зберігає.

## 6. Дизайн-гайд

Структура секцій — з розділу 4.2, **вигляд — новий**. Що можна і треба міняти: палітру, акцентний колір, пару шрифтів, форму карток і кнопок, декор hero, світлу/темну тему.

**Незмінні технічні вимоги:**

- Tailwind v4, тема через CSS-змінні в `globals.css` (`--background`, `--foreground`, `--accent` + похідні). Жодних хардкод-кольорів «на око» по компонентах — акцент задається змінною в одному місці.
- Мобільна версія — обов'язкова й перевірена: hero складається в одну колонку, відгуки — в одну, форма — в одну, горизонтального скролу немає на 375px.
- Контраст тексту й фону — не нижче WCAG AA (4.5:1 для основного тексту). Дрібний приглушений текст (`text-white/50` і подібне) — тільки для другорядного.
- Шрифти — тільки через `next/font/google` з кириличним сабсетом. Ніяких зовнішніх `<link>` на шрифти.
- Обкладинка — через `next/image` з явними `width`/`height` та `priority` (це LCP-елемент).
- Фокус на інтерактивних елементах видимий (не вирізати `outline` без заміни).
- Модалки: `fixed inset-0 z-50`, затемнений оверлей, кнопка закриття, вміст обмежений по ширині й скролиться на малих екранах.
- Кнопка CTA має бути візуально домінантною на сторінці — це головна дія сайту.

## 7. Чого робити не треба

- Не додавати базу даних, авторизацію, кошик, особистий кабінет — цього немає і не потрібно.
- Не приймати й не зберігати номери карток чи будь-які платіжні дані. Оплата — тільки зовнішнім посиланням.
- Не додавати cookie-банер, якщо не додано трекерів, що його вимагають.
- Не робити сайт багатосторінковим — це односторінковий лендинг з якорями.
- Не тягнути UI-бібліотеки (MUI, shadcn, Chakra) заради двох модалок.
- Не комітити `.env`, ключі сервісного акаунта, токени.
- Не лишати в коді дефолтні файли `create-next-app` і згадки попередньої книги.
